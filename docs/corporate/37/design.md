# Design — #37

## Problem

`technical-architect` holds no team-side answer for how Tailwind CSS is wired into a frontend build pipeline, so a design act that must rule on it pays for a live documentation sweep — and pays twice, because Tailwind's current major wires up differently from the one before it, so the version-sensitive half of the answer is rediscovered on the spot. Issue #37 closes that gap by authoring the eighteenth stack playbook skill in this plugin: `tailwind-playbook`.

The deliverable is one plugin component — a `SKILL.md` — plus the repo's own record of what ships. In scope: the three wiring facts the spec names (which packages, which governing configuration file, which stylesheet entry point), stated for the current major and distinguishable from the prior one, traceable to Tailwind's own documentation tree.

Out of scope, per the spec's non-goals and this repo's conventions: any other styling stack; the frontend-framework gap tracked separately (shipped already as `angular-playbook`, `plugins/corporate/skills/angular-playbook/SKILL.md`); any change to a role's `tools:` allowlist; any entry in `plugins/corporate/.mcp.json`; holding the wiring of any past major beyond naming its superseded spellings as traps.

## Approach

One new directory, `plugins/corporate/skills/tailwind-playbook/`, holding a single `SKILL.md` and no sibling files. It follows the playbook contract in `docs/authoring.md:88-172` exactly: `name: tailwind-playbook` matching the directory, a "Use when …" description naming Tailwind's *identifiers* (`tailwindcss`, `@tailwindcss/vite`, `@tailwindcss/postcss`, `@tailwindcss/cli`, `@import "tailwindcss"`, `@theme`, `@source`, `@utility`, `@apply`, `@reference`, `@config`, `tailwind.config.js`, `@tailwind base`, `.postcssrc.json`) rather than only the marketing name, and the five body sections in the fixed order — `## Stack`, `## Toolchain`, `## Obligations by activity`, `## Traps`, `## Resources`. No sixth section, no version-resolution ladder, no `references/` sibling.

Six rulings shape it.

**1. The directory name is the stack identifier, not the package name.** `tailwind-playbook`, so the identifier a `## Stack readiness` row carries is `tailwind` — the same shape as `angular-playbook` (whose package is `@angular/core`) and `docker-playbook`. The package spelling `tailwindcss` is what a request actually contains, so it lives in the `description`, which is where `docs/authoring.md:106-110` says identifiers belong.

**2. The release distinction is not a new section — the format already holds it.** `docs/authoring.md:129-132` fixes this: "name the current package in `## Stack` and the superseded one in `## Traps`". So the spec's requirement 2 is answered by `## Stack` stating v4 flat and `## Traps` carrying the v3 spellings, and requirement 4 — a future wiring change being detectable rather than missed — is answered by two things already in the format: the `## Stack` rule that the major in the project's own `tailwindcss` dependency governs, and the pinned-doc obligation that a fact upstream covers is read there, never asserted from memory. Nothing new had to be invented; a version section would have been a section the contract forbids.

**3. One playbook, one tree, no area split.** Bun gets four playbooks because its own docs split into four areas (`docs/authoring.md:97-102`). `tailwindcss.com/docs` is one tree, so Tailwind gets one file. The pinned doc source row names two URLs and no more: `tailwindcss.com/docs` as the authority, and `tailwindcss.com/docs/installation/framework-guides` as the subtree that holds the per-build-tool wiring. Tailwind publishes no `llms.txt` (both `tailwindcss.com/llms.txt` and `tailwindcss.com/docs/llms.txt` returned 404 on 2026-09-12), so unlike `angular-playbook` the row cannot name an index file — it names the subtree instead, which is what the contract's "the subtree that is this playbook's area" clause allows.

**4. The build tooling vendor's guide is pinned by that vendor's own playbook, not by this one.** The spec's requirement 3 asks the held answer to be traceable to two authorities — Tailwind's installation guide and the build tooling vendor's integration guide. The two-URL cap and the one-playbook-one-tree rule resolve this cleanly rather than by compromise: Tailwind's own per-framework guides *are* where the Tailwind-side wiring for each vendor is stated (F12), so they satisfy requirement 3 inside this file, while the vendor's own tree stays pinned where it already is — `angular.dev` in `plugins/corporate/skills/angular-playbook/SKILL.md:55-56`. Settled here rather than carried into the plan: a second vendor URL in this file would have been a third URL, and it would have rotted independently of the playbook that owns it.

**5. One toolchain, stated absolutely, and it is bun.** Every upstream snippet prints `npm install` or `npx` (F2, F10, F12), and `docs/authoring.md:168-172` requires the translated command to be what lands in the file. So every `## Toolchain` row is `bun` / `bunx`, and `npm`, `npx`, `yarn` and `pnpm` are banned outright, including inside copied snippets. One extra trap falls out of this: the Angular integration guide prints `npm install tailwindcss @tailwindcss/postcss postcss --force` (F12) — `--force` is an npm flag, not a Tailwind package or option, and a bun translation drops it.

**6. No `references/` sibling.** Permitted by `docs/authoring.md:162-165`, but each of the three wiring facts resolves from one page, and a second file doubles the rot surface for no new fact.

### Pinned Tailwind facts (F1–F13)

Every fact the playbook states is fixed here with the source it was fetched from on 2026-09-12. This list is the authority T1 transcribes; nothing about Tailwind is left for the build to decide. A fact the file needs that is absent here is a **design defect to route back**, never a licence to write it from memory.

- **F1 — Release.** `tailwindcss` registry dist-tags: `latest` `4.3.3`, `v3-lts` `3.4.19`, `next` `4.0.0`. `@tailwindcss/postcss`, `@tailwindcss/vite` and `@tailwindcss/cli` each currently publish `latest` `4.3.3` as well. v4 is the current major; for an existing project, the major in its own `tailwindcss` dependency is the one whose rules apply. Source: `registry.npmjs.org/-/package/tailwindcss/dist-tags` and the three `@tailwindcss/*` equivalents.
- **F2 — The three wiring paths, and the packages each needs.** Vite: `tailwindcss` + `@tailwindcss/vite`, the plugin registered in `vite.config.ts` as `plugins: [tailwindcss()]` (source: `tailwindcss.com/docs/installation/using-vite`). PostCSS: `tailwindcss` + `@tailwindcss/postcss` + `postcss`, the plugin registered in `postcss.config.mjs` as `{ plugins: { "@tailwindcss/postcss": {} } }` (source: `tailwindcss.com/docs/installation/using-postcss`). No bundler: `tailwindcss` + `@tailwindcss/cli`, built by `npx @tailwindcss/cli -i ./src/input.css -o ./src/output.css --watch` (source: `tailwindcss.com/docs/installation/tailwind-cli`).
- **F3 — Stylesheet entry point.** One line, identical across all three paths: `@import "tailwindcss";` in the project's CSS entry file. Source: the three installation pages in F2.
- **F4 — The governing configuration file.** v4 is CSS-first: the stylesheet holding `@import "tailwindcss"` *is* the configuration. Theme tokens are declared in a top-level `@theme { … }` block; "Theme variables are special CSS variables defined using the `@theme` directive that influence which utility classes exist in your project." Namespaces include `--color-*`, `--font-*`, `--text-*`, `--breakpoint-*`, `--spacing-*`, `--radius-*`, `--shadow-*`. `--color-*: initial` clears one namespace; `--*: initial` clears every default. Theme variables are also emitted as real CSS custom properties under `:root`. Source: `tailwindcss.com/docs/theme`.
- **F5 — The legacy JS config is opt-in.** `tailwind.config.js` is still supported but "no longer detected automatically"; it is loaded explicitly with `@config "../../tailwind.config.js";`. `corePlugins`, `safelist` and `separator` "are not supported in v4.0". `@plugin` loads a legacy JS plugin. Source: `tailwindcss.com/docs/upgrade-guide`, `tailwindcss.com/docs/functions-and-directives`.
- **F6 — Source detection replaces `content`.** Tailwind scans project files as plain text, skipping `.gitignore`d files, `node_modules`, binary files, CSS files and package-manager lock files. `@source "…"` registers an extra source; `@import "tailwindcss" source("../src")` sets the base path; `@source not "…"` ignores a path; `@import "tailwindcss" source(none)` disables automatic detection; `@source inline("…")` safelists, with brace expansion (`@source inline("{hover:,focus:,}underline")`); `@source not inline("…")` excludes. Source: `tailwindcss.com/docs/detecting-classes-in-source-files`.
- **F7 — Dynamic class names produce nothing.** Tailwind does not parse code, so `class="text-{{ error ? 'red' : 'green' }}-600"` generates no CSS; the complete class name must appear literally, e.g. `class="{{ error ? 'text-red-600' : 'text-green-600' }}"`. Source: same page as F6.
- **F8 — The v3 → v4 wiring delta.** `@tailwind base; @tailwind components; @tailwind utilities;` → `@import "tailwindcss";`. The PostCSS plugin moved out of `tailwindcss` into `@tailwindcss/postcss`, and `postcss-import` and `autoprefixer` can be removed because "imports and vendor prefixing is now handled for you automatically". The CLI moved out of `tailwindcss` into `@tailwindcss/cli`: `npx tailwindcss -i input.css -o output.css` → `npx @tailwindcss/cli -i input.css -o output.css`. `tailwind.config.js` → CSS-first `@theme` (F5). `content` array → automatic detection plus `@source` (F6). Custom utilities: `@layer utilities { .tab-4 { … } }` → `@utility tab-4 { … }`. The important modifier moved from prefix to suffix: `!flex` → `flex!`. Source: `tailwindcss.com/docs/upgrade-guide`.
- **F9 — Renamed and removed utilities.** Renamed: `shadow-sm`→`shadow-xs`, `shadow`→`shadow-sm`, `drop-shadow-sm`→`drop-shadow-xs`, `drop-shadow`→`drop-shadow-sm`, `blur-sm`→`blur-xs`, `blur`→`blur-sm`, `backdrop-blur-sm`→`backdrop-blur-xs`, `backdrop-blur`→`backdrop-blur-sm`, `rounded-sm`→`rounded-xs`, `rounded`→`rounded-sm`, `outline-none`→`outline-hidden`, `ring`→`ring-3`. Removed: `bg-opacity-*`, `text-opacity-*`, `border-opacity-*`, `divide-opacity-*`, `ring-opacity-*`, `placeholder-opacity-*` (use the `/50` opacity modifier), `flex-shrink-*`/`flex-grow-*` (→ `shrink-*`/`grow-*`), `overflow-ellipsis` (→ `text-ellipsis`), `decoration-slice`/`decoration-clone` (→ `box-decoration-*`). Source: `tailwindcss.com/docs/upgrade-guide`.
- **F10 — Upgrade tool.** `npx @tailwindcss/upgrade` automates most of the v3→v4 migration. "The upgrade tool requires Node.js 20 or higher, so ensure your environment is updated before running it." Upstream recommends running it on a new branch and reviewing the diff. Source: `tailwindcss.com/docs/upgrade-guide`.
- **F11 — Compatibility boundaries.** "Tailwind CSS v4.0 is a full-featured CSS build tool designed for a specific workflow, and is not designed to be used with CSS preprocessors like Sass, Less, or Stylus" — "Think of Tailwind CSS itself as your preprocessor". CSS modules can co-exist but are not recommended. Component `<style>` blocks are discouraged; where used, "make sure to import your global styles as reference if you want features like `@apply` to work as expected" — the `@reference` directive, which "imports your main stylesheet for reference without including the styles in the output". Browser floor: Chrome 111, Safari 16.4, Firefox 128; older support means staying on v3.4. Source: `tailwindcss.com/docs/compatibility`, `tailwindcss.com/docs/functions-and-directives`.
- **F12 — Per-build-tool integration guides.** `tailwindcss.com/docs/installation/framework-guides` links one guide each for Next.js, Laravel, Nuxt, SolidJS, SvelteKit, Gatsby, Angular, Ruby on Rails, React Router, TanStack Start, Phoenix, Parcel, Symfony, Meteor, AdonisJS, Ember.js, Astro, Qwik and Rspack. The Angular guide wires the PostCSS path: `ng new my-project --style css`, then `npm install tailwindcss @tailwindcss/postcss postcss --force`, a `.postcssrc.json` holding `{ "plugins": { "@tailwindcss/postcss": {} } }`, `@import "tailwindcss";` in `./src/styles.css`, then `ng serve`. Note that the config filename there is `.postcssrc.json`, not `postcss.config.mjs`. Source: `tailwindcss.com/docs/installation/framework-guides`, `tailwindcss.com/docs/installation/framework-guides/angular`.
- **F13 — Doc tree.** `tailwindcss.com/docs` is the authority. No `llms.txt` index is published — `tailwindcss.com/llms.txt` and `tailwindcss.com/docs/llms.txt` both return HTTP 404 — so exact pages are reached through the docs navigation, and `tailwindcss.com/docs/installation/framework-guides` is the subtree for per-build-tool wiring. Source: direct HTTP checks, 2026-09-12.

### Registration surfaces

A new shipped component is not finished when the file exists. Four enumerations go stale otherwise, all verified open:

- `README.md:263` — "Seventeen ship today: …" and the per-playbook clause list (`README.md:263-277`).
- `README.md:418` — the `Skill` row of the component inventory table.
- `CLAUDE.md:37-41` — the "Shipped" bullet's "seventeen stack playbook skills (…)" list.
- `plugins/corporate/.claude-plugin/plugin.json:4` — version `5.2.0` → `5.3.0`, per the convention that the version bumps on every published change.

`docs/ideas.md` needs **no** edit, unlike issue #36's case: it holds no drafted Tailwind entry (verified — no case-insensitive match for "tailwind" anywhere in the file), so there is no candidate listing that a shipped skill would contradict.

One further edit, and it is a judgement I made rather than one the spec directs: `plugins/corporate/skills/angular-playbook/SKILL.md:98-102` lists `typescript-playbook`, `bun-pm-playbook`, `nginx-playbook` under `### Skills`, and `tailwind-playbook` belongs beside them — the incident that produced this spec was an Angular design act, the Angular integration guide is F12, and `## Resources` is names-only so the edit is one line with no summary to rot (`docs/authoring.md:144-146`). It does not reopen the frontend-framework gap the spec defers; that playbook already ships.

## Rejected

- **One broad `frontend-playbook` or `styling-playbook` with per-stack sections.** Lost to `docs/authoring.md:94-95` — a narrow description routes better, and a broad one fires on stacks the file cannot answer for — and to the spec's third non-goal.
- **Split Tailwind into `tailwind-playbook` + `tailwind-config-playbook`, as Bun is split into four.** Lost because the area split exists only for stacks whose upstream docs split into areas (`docs/authoring.md:97-102`); `tailwindcss.com/docs` is one tree, so a split would be a taxonomy of our own and would duplicate the ban lane.
- **Add a sixth `## Versions` section, or a version-resolution ladder, to satisfy the spec's release-distinction requirement.** Lost to `docs/authoring.md:129-132`, which forbids both by name and prescribes exactly the current-in-`## Stack` / superseded-in-`## Traps` split this design uses. The requirement is met without a section the contract bans.
- **Add a `references/` sibling mapping each wiring decision to its exact page.** Permitted by `docs/authoring.md:162-165` but lost on "a sibling exists only when it carries a real delta" — each of the three wiring facts resolves from a single page, and a second file doubles the rot surface for no new fact.
- **Pin a third URL for the build tooling vendor's own integration guide** (e.g. `angular.dev`, `vite.dev`), to answer the spec's requirement 3 literally. Lost to the two-URL cap in `docs/authoring.md:158-161` and to the fact that `plugins/corporate/skills/angular-playbook/SKILL.md:55-56` already pins `angular.dev`. Tailwind's own per-framework guides (F12) carry the Tailwind-side wiring for each vendor, which is what requirement 3 actually needs held.
- **Name the stack `tailwindcss-playbook`, matching the npm package.** Lost to consistency with `angular-playbook` and `docker-playbook`: the directory carries the stack identifier a `## Stack readiness` row uses, and the package spelling belongs in the description, where triggers are matched (`docs/authoring.md:106-110`).
- **Add nothing at all — let the architect keep fetching live.** Lost to the spec's Problem statement: that recurring cost is the whole reason the record exists, and it leaves downstream roles unable to check a design's Tailwind facts without redoing the sweep.
- **Merge authoring and registration into one task.** Lost to the file-boundary rule — the sets are disjoint, so splitting buys real parallelism and costs nothing.
- **Leave `plugins/corporate/skills/angular-playbook/SKILL.md` untouched.** Lost because `## Resources` is names-only and one line, the Angular guide is the pinned F12 integration path, and two adjacent playbooks invisible to each other is exactly the staleness the registration convention exists to prevent.
- **Edit `docs/ideas.md` as issue #36 did.** Rejected on fact, not on judgement: the file holds no Tailwind entry, so there is nothing to mark shipped and any edit would be invention.

## Risks

- **Version rot.** `## Stack` names v4 and `4.3.3`. Tailwind's major cadence is slower than Angular's, but the line still needs a bump per major. Partly self-correcting: the pinned-doc obligation is what an agent hits before asserting a wiring fact, and F13 is where the check lands.
- **The silent renames are the sharpest hazard the file carries, and also the easiest to get subtly wrong when transcribing.** `shadow-sm`, `rounded-sm`, `blur-sm`, `drop-shadow-sm` and `backdrop-blur-sm` all exist in both majors with *different* meanings (F9), so a mis-transcribed row would actively mislead. T1's steps therefore require these to be copied from F9 rather than recalled.
- **v3 remains supported and in the wild** (`v3-lts` `3.4.19`, F1), and the browser floor (F11) is a legitimate reason for a project to stay there. A `## Stack` that reads only "v4" could be applied to a v3 project; mitigated by the rule that the project's own `tailwindcss` major governs, but an agent skimming only the trap list could still misapply it.
- **`bun add` against a non-bun project.** A consumer workspace installed with npm still resolves these packages, but mixing installers risks lockfile drift. The playbook states one toolchain absolutely, per convention, and leaves the lockfile rule to `bun-pm-playbook` — a stated policy, not an accident, but the place a consumer project feels friction first.
- **Upstream page moves.** With no `llms.txt` to resolve pages (F13), the pinned row names a tree and a subtree rather than an index; a restructured docs site degrades the pin to navigation rather than breaking it, which is the intended failure mode but a weaker one than `angular-playbook` enjoys.
