# Design — #36

## Problem

`technical-architect` has no team-held guidance for Angular, so every design act that must rule on Angular pays for a live documentation sweep, and no downstream role can check the resulting facts without repeating it. Issue #36 closes that gap by authoring the seventeenth stack playbook skill in this plugin: `angular-playbook`.

The deliverable is one plugin component — a `SKILL.md` — plus the repo's own record of what ships. In scope: the four rulings the spec names (which major, which scaffolding options, the build output contract, the static-serving contract), the current-practice orientation (signals, standalone, built-in control flow), and the conditional preference for the Angular CLI MCP server's tooling.

Out of scope, per the spec's non-goals and this repo's conventions: any other frontend framework; any change to a role's `tools:` allowlist; any entry in `plugins/corporate/.mcp.json`; the deferred generic MCP-access-by-task-scope ticket.

## Approach

One new directory, `plugins/corporate/skills/angular-playbook/`, holding a single `SKILL.md` and no sibling files. It follows the playbook contract in `docs/authoring.md:88-172` exactly: `name: angular-playbook` matching the directory, a "Use when …" description naming Angular's *identifiers* (`angular.json`, `ng`, `@angular/core`, `ng serve`, `@if`/`@for`, `signal()`, `dist/<project>/browser`) rather than only the marketing name, and the five body sections in the fixed order — `## Stack`, `## Toolchain`, `## Obligations by activity`, `## Traps`, `## Resources`. No sixth section, no version-resolution ladder, no `references/` sibling.

Three design rulings shape the content.

**1. The MCP preference is an obligation keyed to activity, not a copy of the server's protocol.** Two in-repo rules pull against each other here, and I settled it rather than carrying it forward: `docs/authoring.md:134-143` forbids restating what another component broadcasts ("an MCP server that broadcasts 'call `list_projects` first' … needs no second copy here"), and `docs/ideas.md:86-94` says the same in stronger terms, while the spec's functional requirement 6 demands the guidance actually direct an agent to prefer that tooling. The resolution: `## Resources` → `### MCP servers` carries the bare name `angular-cli` and nothing else (names-only rule, `docs/authoring.md:144-146`), and the preference lives in `## Obligations by activity` as *our* rule keyed to *our* activities — scaffolding help, best-practice lookup, build and dev-server verification — with the `## Toolchain` commands named as the fallback when the server is absent. That satisfies requirement 6 without the playbook becoming a mirror of a component we do not own, and it honours the degrade-gracefully rule (`docs/authoring.md:147-148`): the plugin ships no such server and the file never implies it does.

A related trap gets absorbed the same way: the dev-server tool names differ between sources — `angular.dev/ai/mcp` prints `devserver.start` / `devserver.stop` / `devserver.wait_for_build`, while the server as exposed in this environment's session names them `devserver_start` / `devserver_stop` / `devserver_wait_for_build`. The playbook therefore refers to the dev-server tools by task and never pins the separator; the five tools whose names agree in both sources (`list_projects`, `get_best_practices`, `search_documentation`, `run_target`, `onpush_zoneless_migration`) may be named literally.

**2. One toolchain, stated absolutely, and it is bun.** Upstream prints `npx @angular/cli …` throughout; `docs/authoring.md:168-172` requires the translated command to be what lands in the file, so every `## Toolchain` row is `bunx`, and `npm`, `npx`, `yarn` and `pnpm` are banned outright — including inside copied doc snippets. This is load-bearing rather than cosmetic because `ng new` takes `--package-manager bun` as a documented allowed value, so the workspace it scaffolds is bun-native from the first command.

**3. One playbook, one tree, no area split.** Bun gets four playbooks because its own docs split into four areas (`docs/authoring.md:97-102`). `angular.dev` is one tree behind one index, so Angular gets one file. The pinned doc source row names two URLs and no more: `angular.dev`, whose exact pages resolve through `angular.dev/llms.txt`, and `angular.dev/assets/context/best-practices.md`, which is upstream's own machine-readable statement of current practice — precisely what the spec's requirement 5 asks the guidance to be traceable to. Fallback when that tree is unreachable: the MCP server's own documentation and best-practice tools where present, otherwise the installed `@angular/*` packages' type definitions.

### Pinned Angular facts (F1–F11)

Every fact the playbook must state is fixed here, with the source it was fetched from on 2026-09-12. This list is the authority T1 transcribes; nothing about Angular is left for the build to decide.

- **F1 — Release.** `@angular/core` registry `latest` is `22.1.6` and `@angular/cli` `latest` is `22.1.8`; `v21-lts` (`21.2.23`) and `v20-lts` (`20.3.31`) dist-tags exist alongside it. v22 is the current major and what a new workspace scaffolds on; for an existing workspace, the major in its own `@angular/core` is the one whose rules apply. Source: `registry.npmjs.org/-/package/@angular/core/dist-tags`, `registry.npmjs.org/-/package/@angular/cli/dist-tags`; corroborated by the docs footer "Built by Angular at v22.1.6".
- **F2 — Builder.** `@angular/build:application` is the default builder for applications generated by `ng new`; it compiles, bundles and minifies through esbuild and can emit a client bundle, a Node server and build-time prerendered routes. Source: `angular.dev/tools/cli/build`.
- **F3 — Build output contract.** The base output directory is `dist/<project>/`. `outputPath` accepts a string (the base) or an object whose keys default as: `browser` → `browser`, `server` → `server`, `media` → `media` (inside the browser directory); `base` has no default and is required in the object form. So the client artifacts of a default build land in `dist/<project>/browser`, and a server build in `dist/<project>/server`. Source: `angular.dev/reference/configs/workspace-config`, `angular.dev/tools/cli/deployment`.
- **F4 — Static-serving contract.** The `browser` directory is the document root, and a routed SPA requires the server to "return the application's host page (`index.html`) when asked for a file that it does not have". `<base href>` is the preferred mechanism for URL resolution and is set at runtime in the HTML; the build-time `--deploy-url` hardcodes paths and is the fallback. Source: `angular.dev/tools/cli/deployment`.
- **F5 — Scaffolding options.** `ng new` accepts `--package-manager` ∈ {`bun`, `npm`, `pnpm`, `yarn`}; `--ai-config` ∈ {`claude-code`, `cursor`, `gemini-cli`, `none`, `open-ai-codex`, `vscode`}; `--style` ∈ {`css`, `less`, `sass`, `scss`, `tailwind`}; `--view-encapsulation` ∈ {`Emulated`, `None`, `ShadowDom`}; booleans `--ssr`, `--routing`, `--zoneless`, `--minimal` (default `false`), `--defaults` (default `false`), `--skip-tests` (default `false`), `--standalone` (default `true`), `--strict` (default `true`). No default is documented for `--ssr`, so this team names it explicitly at scaffold time — the output contract in F3 differs depending on it. Source: `angular.dev/cli/new`.
- **F6 — Zoneless.** "Zoneless is the default in Angular v21+ so you do not need to do anything to enable it." `--zoneless` is therefore not part of a v22 scaffold; zone.js is removed by dropping `zone.js` and `zone.js/testing` from `polyfills` in `angular.json`. Source: `angular.dev/guide/zoneless`.
- **F7 — Tests.** Vitest is the default test runner for new Angular CLI projects, run by the `@angular/build:unit-test` builder via `ng test`. Karma is still supported but is no longer the default and has a documented migration path. Source: `angular.dev/guide/testing`.
- **F8 — Current practice.** From upstream's own context file: standalone components always, and never set `standalone: true` (the default from v20+); never set `ChangeDetectionStrategy.OnPush` explicitly (the default from v22+); signals for state, with `input()`, `output()`, `model()`, `computed()` and `linkedSignal()` in place of the decorator forms, and `update`/`set` rather than `mutate`; native `@if` / `@for` / `@switch` in place of `*ngIf` / `*ngFor` / `*ngSwitch`; host bindings in the `host` object, not `@HostBinding`/`@HostListener`; `class`/`style` bindings, not `ngClass`/`ngStyle`; never import `CommonModule` — import only the directives and pipes the template uses; `inject()` rather than constructor injection; `@Service` preferred over `@Injectable({providedIn: 'root'})` for new singletons (v22+); Signal Forms (`@angular/forms/signals`) preferred for new forms, stable in v22+, and Reactive over Template-driven otherwise; `NgOptimizedImage` for static images (not inline base64); lazy-loaded feature routes; strict TypeScript, no `any`, `unknown` where uncertain. Source: `angular.dev/assets/context/best-practices.md`.
- **F9 — MCP server.** Upstream starts it as `npx @angular/cli mcp` → `bunx @angular/cli mcp` here. Documented tools: `ai_tutor`, `get_best_practices`, `list_projects`, `onpush_zoneless_migration`, `run_target`, `search_documentation`, plus the dev-server trio (see the naming divergence above). Upstream calls it experimental and documents no minimum CLI version. Source: `angular.dev/ai/mcp`; tool inventory corroborated by the `angular-cli` server instructions present in this environment's session.
- **F10 — Doc tree.** `angular.dev/llms.txt` is the index; `angular.dev/assets/context/llms-full.txt` is the full context file; `angular.dev/assets/context/best-practices.md` is the best-practice rules file. Source: `angular.dev/ai/develop-with-ai`.
- **F11 — CLI surface.** The documented commands are `add`, `analytics`, `build`, `cache`, `completion`, `config`, `deploy`, `e2e`, `extract-i18n`, `generate`, `lint`, `new`, `run`, `serve`, `test`, `update`, `version`. `mcp` is *not* among them, which is why the MCP row keeps the `bunx @angular/cli mcp` spelling rather than `bunx ng mcp`. `ng update` is documented only as "updates your workspace and its dependencies" with no argument form on that page, so no package arguments are asserted here. Source: `angular.dev/cli`.

### Registration surfaces

A new shipped component is not finished when the file exists — four in-repo enumerations go stale otherwise, all of them verified open:

- `README.md:263` — "Sixteen ship today: …" and the per-playbook clause list (`README.md:263-277`).
- `README.md:417` — the `Skill` row of the component inventory table.
- `CLAUDE.md:37-43` — the "Shipped" bullet's "sixteen stack playbook skills (…)" list. In scope: it documents what ships, and the brief left the judgement to me.
- `docs/ideas.md:52-117` — the drafted `angular-playbook` entry, whose status line reads "drafted — but the family format it needed now exists". `README.md:274-275` points readers at `docs/ideas.md` for *candidates*, so a shipped skill still listed as a candidate is a contradiction in the repo's own map. The later reference at `docs/ideas.md:305` belongs to a different entry and needs no change.
- `plugins/corporate/.claude-plugin/plugin.json:4` — version `5.1.0` → `5.2.0`, per the convention that the version bumps on every published change, a new component being a feature.

## Rejected

- **Register the `angular-cli` server in `plugins/corporate/.mcp.json`.** Lost on three counts: the spec's third non-goal forbids a standing grant; `docs/authoring.md:237-239` says an MCP server's tool schemas cost context in every session and to prefer a skill where no long-lived process is needed; and `docs/ideas.md:109-111` already ruled the server user-level, bring-your-own. The conditional in-guidance preference delivers requirement 6 at zero per-session cost.
- **One broad `frontend-playbook` with per-framework sections.** Lost to the spec's first non-goal and to `docs/authoring.md:94-95` — a narrow description routes better, and a broad one would fire on frameworks the file cannot answer for.
- **Split Angular into `angular-playbook` + `angular-cli-playbook`, as Bun is split.** Lost because the area split exists only for stacks whose upstream docs split into areas (`docs/authoring.md:97-102`); `angular.dev` is one tree behind one index, so a split would be a taxonomy of our own and would duplicate the ban lane.
- **Add a `references/` sibling mapping each decision to its exact page.** Permitted by `docs/authoring.md:162-165` but lost on "a sibling exists only when it carries a real delta" — the two pinned URLs resolve all four spec rulings from one page each, and a second file would double the rot surface for no new fact.
- **Restate the MCP server's own protocol in the body** (the shape `docs/ideas.md:99-104` sketched, with rows like "never shell out to `ng` when a tool covers it"). Lost to `docs/authoring.md:134-143`: it couples this file to a component we do not own and rots when that component is renamed or fixed. Requirement 6 is met by naming our tasks and our fallback instead.
- **Add nothing at all — let the architect keep fetching live.** Lost to the spec's Problem statement: that recurring cost is the whole reason the record exists, and it leaves downstream roles unable to check a design's Angular facts without redoing the sweep.
- **Merge authoring and registration into one task.** Lost to the file-boundary rule — the sets are disjoint, so splitting buys real parallelism and costs nothing.
- **Leave `docs/ideas.md` and `CLAUDE.md` untouched, editing only `README.md`.** Lost because both name what ships; a shipped skill still filed as a candidate and a "sixteen" count that is now seventeen are the same staleness the brief asked me to judge, and it is cheap to prevent in the same pass.

## Risks

- **Version rot.** `## Stack` names v22, and Angular ships a major roughly every six months, so the line needs a one-line bump per release. Partly self-correcting: the pinned best-practices file is maintained upstream and versions its own claims ("default in Angular v20+", "stable in v22+"), and the obligation to read it is what catches drift.
- **Version-keyed practice applied to an older workspace.** F8's rules are keyed to defaults introduced in v20, v21 and v22. On a workspace pinned to v19 or earlier, "never set `standalone: true`" is wrong. Mitigated by the `## Stack` rule that the workspace's own `@angular/core` major governs, but an agent skimming only the practice list could still misapply it.
- **MCP tool-name divergence** between `angular.dev/ai/mcp` and the server as exposed in a session is unresolved upstream; the playbook sidesteps it by naming the dev-server tools by task, which means an agent must read its own tool list to call them. Acceptable, and better than pinning a separator that is wrong in one of the two sources.
- **`bunx ng` against a non-bun workspace.** A consumer workspace scaffolded with npm still has an `ng` binary `bunx` will run, but mixing installers risks lockfile drift. The playbook states one toolchain absolutely, per convention, and leaves the lockfile rule to `bun-pm-playbook` — this is a stated policy, not an accident, but it is the place a consumer project will feel friction first.
