# Crypto Playbook

## Stack

Cryptography is chosen, never built. Every primitive comes from the runtime's own
library or from a maintained one; which binding a project uses is a per-project
decision, ruled in the design. This playbook is the engine, not a binding.

Four jobs, and confusing two of them is the defect:

| Job | Means | Primitive |
|---|---|---|
| hash | a secret nobody ever needs back, only verified | slow password KDF |
| derive | turning a password into a key | KDF with a salt and a length |
| authenticate | proving bytes were not altered | HMAC or a signature |
| encrypt | bytes that must come back out | AEAD |

- Passwords: **Argon2id** is the default. scrypt and bcrypt are acceptable where
  it is unavailable, PBKDF2 where a certification requires it.
- Cost parameters are a written decision with a verify time measured on target
  hardware — never a constant copied from an example, and never left implicit.
- The stored value is a self-describing hash string carrying algorithm,
  parameters and salt. A schema storing the hash alone cannot be upgraded.
- Tokens — reset, verification, session, API key — are at least 128 bits of
  CSPRNG output, and what is stored is their hash.
- Anything encrypted implies a key location and a rotation story. Both are named
  in the design, in the same message as the algorithm.

## Toolchain

| Job | Command |
|---|---|
| read a stored hash's algorithm and parameters | `cut -d'$' -f2,3 <<<"$HASH"` |
| generate a 256-bit token | `openssl rand -base64 32` |
| digest a file | `openssl dgst -sha256 file` |
| HMAC a file | `openssl dgst -sha256 -hmac "$KEY" file` |
| list available digests | `openssl list -digest-algorithms` |

These inspect and calibrate. None of them produces a value that ships: a
production hash, key or token is generated by the application's own library, on
the path that will later verify it.

Never implement a primitive — no hand-rolled KDF loop, no homemade
constant-time compare, no bespoke token or hash format, no "just one round of
SHA-256 first". A fast digest is not a password hash, whatever it is wrapped in.

## Obligations by activity

| Activity | Obligation |
|---|---|
| any | `cheatsheetseries.owasp.org` is the index that resolves a question to its page and is the authority; `references/docs-map.md` beside this file maps the decisions this team makes to the exact page, OWASP or normative spec. A fact either covers is read there, never asserted from memory, and no blog post, vendor guide or SDK README substitutes for it |
| choosing an approach | name the job — hash, derive, authenticate, encrypt — before naming an algorithm, then fix the algorithm and its parameters in writing with the verify time measured on target hardware. Anything encrypted names where its key lives and how it rotates, in the same message |
| implementing | CSPRNG for every salt, nonce and token; parameters carried in the stored hash string, never as a constant the code assumes; constant-time comparison for every secret; a secret, a key or a hash never logged, never in an error message, never in a URL |
| migrating | rehash on successful login whenever the stored parameters differ from current policy — that is the upgrade path, per record, on next use. A forced global reset is a last resort, not the default, and a legacy hash that cannot wait is wrapped rather than left |
| reviewing | reject a fast digest for a password, a shared or missing salt, `==` on a secret, a hand-rolled KDF, a key or pepper committed to the repo, encryption where hashing was the requirement, a hash column with no algorithm in it, and a nonce whose uniqueness argument is not stated |
| testing | the negative cases are the suite: wrong password, tampered hash, unknown user, a stored hash at superseded parameters proving the rehash fires. A green happy path proves nothing here |

## Traps

- Fast hashes are wrong for passwords by design. SHA-256 in a loop is not a KDF,
  however many rounds — the work factor has to be a parameter that can be raised
  later, and memory hardness is the property that defeats GPU cracking.
- Salt is per-record and public; it defeats precomputation, nothing else. Pepper
  is a secret key held outside the database — a key-management commitment with a
  rotation story, not a free upgrade.
- bcrypt truncates its input at 72 bytes, silently. Pre-hashing to dodge that
  introduces a null-byte problem when the digest is passed raw, and a password
  shucking exposure when the pre-hash is unsalted.
- Cost parameters expire. A work factor chosen years ago is not today's; verify
  time on real hardware is the measure, and the number needs a review date, not
  a comment.
- User enumeration leaks through timing: returning early because the account
  does not exist is measurable from outside. Verify against a dummy hash and
  return the same answer in the same time.
- Nonce reuse under one AEAD key is catastrophic — it loses confidentiality and,
  for GCM, the authentication key itself. A repeated salt is merely weak; a
  repeated nonce is fatal.
- Ciphertext without authentication is malleable. AEAD, or encrypt-then-MAC.
  Nothing else, and never MAC-then-encrypt.
- `Math.random()` is not a CSPRNG, and a UUID from a library that does not
  promise one is not a token.
- A high-entropy secret the server itself issued — an API key, a session id, a
  reset token — is stored hashed, and there a fast digest is the correct choice:
  the input is already unguessable, so a slow KDF buys nothing and costs a
  request. That is the one exception, and it exists because the threat is a
  leaked table, not a guessed input.
- Ciphertext carries a key identifier from its first write, or rotation is a
  migration nobody can run.
- "Encrypted passwords" is a design error, not a wording error. Anything
  reversible is recoverable by whoever takes the key.
